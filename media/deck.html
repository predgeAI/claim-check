The problem

The half of code review nobody budgets for

Reading the diff is the visible half. The other half is checking that every claim the author made is true in the code. Under load, reviewers skip it. Here is a senior maintainer doing it by hand, this month:

What it does

Turn prose into claims, then check every one at once

01

Extract

Read the description and the review thread. Keep only claims a reader could falsify; drop intent, opinion and future tense.

02

Fan out

One Bob subagent per claim, running in parallel, each with full repository context and none seeing the others.

03

Verify

Each returns holds, does not hold or cannot tell — and the file:line that settles it. Cannot tell is never dressed up as holds.

04

Report

A ledger ordered by what should stop a merge: failures first, unchecked next, passes folded away.

Application of technology3
Why it needs IBM Bob 2.0

Each Bob capability carries a different part of the work

Document understanding
The claims live in prose — a PR body and a review thread — not in a list.
Full repository context
The evidence for one claim is spread across files and survives a rebase.
Subagents
One per claim, isolated: a hard claim stalls only itself, and no verdict biases another.
Parallel tasks
N independent searches at once — the difference between once-per-PR and every push.

Built inside Bob IDE across five sessions. The prompts are in the repository in the order they ran; nothing in src/ was written by hand.

Run on the diff alone to save budget, a subagent found the guarded path, stopped, and said holds.

“Every request is guarded” is universal: one example cannot confirm it, only a counterexample refutes it. Universal claims now must search every call site and list what they checked.
